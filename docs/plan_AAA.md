## 0. 如何阅读本文档

四条使用原则：

1. **顺序是硬约束，不是建议。** 第一梯队未完成前做第二梯队会浪费投入——在 120ms 的最坏帧上叠加全屏后处理只会让体验更差。梯队之间存在技术依赖，文中每项都标注了前置条件。
2. **多人联机已立项，这个决策向前渗透。** 它不是文档末尾的一个可选项，而是重新定义了第 8.1 节模块拆分的边界方向。凡是标注「MP 约束」的段落，都是这个决策带来的、从今天起就生效的硬性要求。详见 [第 9 节](#9-多人联机已立项)。
3. **"3A" 在这里是方向而非终点。** 3A 的定义包含数百人团队、数千万美元预算与多年工期。一个 3.8 万行、零构建的浏览器项目不可能通过补丁变成 3A。本文档的实际目标是：**消除"廉价感"的具体来源，把项目推到商业级独立游戏的完成度上限**。
4. **每一项都给了代码证据。** 结论可以质疑，但请先核对引用的行号与数值。所有数字来自当前仓库实测，不是估计。

工作量标注为**人日**粗估，假设执行者熟悉本代码库；对不熟悉者应乘以 1.5–2。

## 1. 执行摘要

### 项目当前定位

**完成度很高的单人浏览器"迷你无人深空 × 迷你 Minecraft"。**

强项明确：确定性无限宇宙、跨星系跃迁、座舱飞行与着陆辅助、24 生物群系、嘉年华园区、以及写得相当扎实的存档事务层（写后回读校验、journal 交换恢复、损坏档隔离、v3→v6 迁移）。这些不是 demo，是实质系统。

弱项同样明确：帧时不稳、视距短、光照层缺失、遭遇战重复、无叙事、无联机、工程骨架扛不住继续加内容。

### 与 3A 的差距一句话概括

> 差距不在"缺少某些功能"，而在**三道互相独立的结构性天花板**：数据布局锁死了视距和帧时，渲染缺整整一层光照，工程架构无法承载继续扩张。

### 最高优先的三件事

| 序号 | 事项 | 为什么是它 |
|---|---|---|
| 1 | 网格化移出主线程 + greedy meshing | 解锁一切画面提升的前置条件；当前性能基线接受 120ms 最坏帧 |
| 2 | 全场景级联阴影（CSM） | 单位投入观感收益最高；目前只有树叶投影，画面因此发平 |
| 3 | 按客户端/服务端轴拆解 `js/main.js` | 决定前两件事之后还能不能持续做下去，且已被联机决策锁定了拆分方向 |

### 已确定的战略方向

**多人联机专门立项（方案 A）。**

这个决策已经做出，本文档据此更新。它带来三条从现在起就生效的硬约束：

1. **权威模拟必须零渲染依赖。** 第 8.1 节的模块拆分从「按功能分层」改为「按客户端/服务端分层」，判据是 `core/` 能在 Node 里跑完整一帧而不加载 three.js。
2. **渲染插值从可选优化升级为必需品。** 因此新增为第一梯队条目（[5.6](#56-渲染插值多人联机的前置条件)）。
3. **存档 v7 必须按「世界共享 / 玩家私有」切分。** 好消息是现有 v6 结构已经存在这条天然接缝。

好消息是这个代码库对联机的适配度**远高于预期**：世界确定性生成（不需要同步地形）、存档格式已经就是「种子 + 编辑增量」（就是网络状态模型）、固定 60Hz 步长已存在、生物 AI 对 three.js 的依赖只有 18 处且多数是当数学库用。详见 [第 9 节](#9-多人联机已立项)。

## 3. 三道结构性天花板

### 天花板 A：数据布局锁死视距与帧时

四个互相加固的约束：

1. **网格化在主线程。** `MeshBuilder.build()` 由 `js/world/infinite.js` 的 `stream()` 直接同步调用。生成已进 Worker，网格化没有。
2. **逐面发射 quad，无 greedy meshing。** 每个可见面独立 4 顶点 / 6 索引。
3. **整柱存储，无 Y 分段。** 外围区块按 `32×256×32` 存（约 1MB 体素数据/区块），`relight` 一次扫整柱。
4. **256³ 密集核心常驻。** `FiniteWorld` 的 256×256×256 `Uint16` 方块 + 两份 `Uint8` 光照 ≈ 64MB，玩家走远也不卸载（为存档逐位兼容付出的常驻税）。

后果是可量化的：渲染半径只有 5 个区块（160 格），雾墙压在 240 格，而项目自己的性能回归测试把"最坏 120ms"当作通过线：

```js
// test/stream_perf_test.js:158-160
// 最坏帧 = 预算 + 单个最大步骤（同步回退路径的
// ensureChunk 级联可达数十毫秒），这里只约束不出现无界长尾
check('单次 stream 消耗有界 (worst=' + worst + 'ms <= ~120ms)', worst <= 120);
```

120ms 对应约 8fps。60fps 的预算是 16.6ms，差一个数量级。这不是调参能解决的，必须改数据布局。

### 天花板 B：渲染缺整整一层光照

场景里**零个 `THREE.Light`**。所谓"实时光影"只覆盖树叶：

```js
// js/systems/shadow.js:11-17
var casters = [];        // 主场景中的树叶 Mesh 列表
var level = 0;           // 0=关 1=中 2=高（对应设置项 shadows）
var RT_SIZE = [0, 768, 1536];
var RANGE = 46;          // 阴影盒半径（格）
var DIST = 110;          // 相机沿太阳反方向后撤距离
var NEAR = 30, FAR = 210;
```

单级正交盒、半径 46 格、2×2 PCF、只登记 `fmesh`（树叶网格）为 caster。**地形、山体、建筑、城堡、飞船、生物一律不投影。**

其余"像光照"的东西都是烘焙或解析：Minecraft 式 0–15 天光/块光、4 档顶点 AO（`var AO = [0.5, 0.72, 0.86, 1.0]`）、正弦噪声云影、`dot(N,sun)*0.62+0.38` 的 wrap 漫反射。

缺失清单：PBR 材质、级联阴影、全局光照、SSAO/GTAO、SSR、HDR 色调映射（`bloom.js` 注释里明确拒绝了 ACES）、TAA/FXAA/SMAA、运动模糊、景深、体积光、体积云、大气散射。

### 天花板 C：工程骨架扛不住继续扩张

- **无模块系统。** 全库零 `import`/`export`，64 个同步 `<script>` 靠加载顺序当 ABI。Worker 里要伪造 `window = self` 才能 `importScripts` 复用同一套脚本。
- **上帝对象。** `js/main.js` 7,448 行、70+ 公开方法，横跨库存 / 合成 / 旅行事务 / 熔炉箱子 / 乐园经济 / 主循环 / 测试钩子。
- **零类型、零静态检查。** 物品 ID 是散落各处的魔法数字（103 / 106 / 122）。重构只能靠跑完整 Puppeteer 套件验证。
- **循环依赖 + 生产代码读测试钩子。** `Controls ↔ Game ↔ Player` 互相回调；`achievements.js` 和 `codex.js` 通过 `Voxel.Game._test.galaxy()` 取数据。
- **模拟与表现未分离。** 没有任何一条边界把「世界状态」和「怎么画出来」隔开 —— 典型例子是 `js/player/player.js:186-191` 在物理更新内部直接写 `Voxel.Game.camera`。

> **联机立项后，这道天花板的性质变了。** 它原本只是「加内容越来越慢」的效率问题，现在成了硬阻塞：没有客户端/服务端边界，权威模拟无法脱离浏览器运行，联机无从谈起。这也是 [8.1](#81-核心表现分层重构含打包器) 的工作量从 25–40 上调到 40–60 人日的原因。
>
> 相对乐观的是：审计发现模拟层对 three.js 的实际依赖很浅（`mobs.js` 1166 行仅 18 处、`js/player/` 仅 6 处），这道天花板比它看上去的要薄。详见 [9.3](#93-这个代码库的四个先天优势)。

## 5. 第一梯队：帧时与视距

> **为什么必须最先做**：所有画面提升都要花帧预算。当前最坏帧 120ms，任何全屏 pass 加上去都是负收益。同时视距 160 格是玩家 30 秒内感知到"世界很小"的直接原因。

### 5.1 网格化移出主线程 + 引入 greedy meshing

**现状证据**

网格构建用 JS 增长数组，每区块三组共 21 个数组：

```js
// js/world/mesh.js:720-726
function build(cx, cz) {
  var CFG = Voxel.Config;
  var H = CFG.WORLD_H, CS = CFG.CHUNK;
  var o  = { pos: [], uv: [], col: [], idx: [], lgt: [], nrm: [], flg: [] };
  var w  = { pos: [], uv: [], col: [], idx: [], lgt: [], nrm: [], flg: [] };
  var fl = { pos: [], uv: [], col: [], idx: [], lgt: [], nrm: [], flg: [] };
```

逐面剔除后直接发射独立 quad，无相邻面合并：


`makeGeo()` 再把 JS 数组拷进 `Float32BufferAttribute` —— 每区块一次大规模临时分配 + 一次拷贝。

调度侧，`stream()` 在主线程轮转三类步骤，预算只在**步骤之间**检查：

```js
// js/world/infinite.js:1155-1170

  if (elapsed >= budgetMs) break;
  var step = 0;

    case 1: m1 = canMesh ? (FiniteWorld.buildMeshes(1, scene) || 0) : 0; step = m1; break;
```

单步内部的 `ensureChunk`（装饰 + `relight` 扫 32×256×32 + 3×3 块光 BFS + 邻域标脏）可以独占几十毫秒，预算管不住。

**目标**

- 主线程每帧网格化耗时 ≤ 2ms（只做几何上传，不做构建）
- 相同视距下顶点数下降 60% 以上（greedy 对大片平坦地形收益最大）
- 走动时不再出现可感知的 chunk 卡顿

**具体做法**

1. 新增 `js/world/mesh_worker.js`。当前只有 1 个生成 Worker（`ensureWorker()`，`WC_MAX_INFLIGHT = 4`），网格 Worker 应独立并支持 2–4 个实例。
2. Worker 输入需要 `33×H×33` 的 pad 体素 + 光照切片；用 `Transferable` 传输（现有 gen worker 已用 `slice()` + transfer 模式，可复用）。
3. Worker 输出直接是 `Float32Array` / `Uint32Array`，主线程只做 `new THREE.BufferAttribute()` 包装。
4. 几何缓冲预分配 + 容量翻倍策略，替换 `pos: []` 增长数组。
5. Greedy meshing：按 6 个朝向分别做 2D 扫描合并，合并键为 `(tileIndex, 顶点光照四元组, AO 四元组, tint)`。**注意**：光照和 AO 是逐顶点的，只有四角完全一致的相邻面才能合并，实际合并率会低于纯 Minecraft 场景，但平坦地面/墙面/海面收益仍然显著。
6. 保留同步回退路径（`file://` 与 CSP 受限环境）。

**验收标准**

- `test/stream_perf_test.js` 的最坏帧断言从 120ms 收紧到 20ms
- 新增顶点数回归测试：固定种子下三个代表性区块（平原/山地/森林）的顶点数不高于基线
- 现有 Puppeteer 套件全绿，`terrain_parity_test.js` 的黄金值不变（几何合并不得改变可见结果）

**风险**

- Greedy 合并与顶点 AO/光照插值交互复杂，容易产生接缝。需要像素级截图对比测试。
- 床/楼梯/台阶/门/十字面片（`def.box` / `def.boxes` / `def.cross` / `def.connector`）不参与 greedy，需保持独立路径。

### 5.2 体素存储改 Y 分段（section）

**现状证据**

```js

WORLD_H: 256,        // v7：限高提升到 256
WORLD_D: 256,
```

- 外围区块：`32×256×32` 方块（`Uint16`）+ sky（`Uint8`）+ blk（`Uint8`）≈ **1.0MB / 区块**
- `STREAM_KEEP_RADIUS: 8` → 最多 17×17 ≈ **290MB** 体素数据（不含几何）
- `viewBoost` 开启后 keep 半径约 11 → 23×23 ≈ **530MB**
- 另有 256³ 密集核心常驻 ≈ **64MB**，且 Worker 侧 `GenCore.store` 与主线程 `absorbShell` 各留一份

而实际内容高度远低于 256：

```js

GEN_ENVELOPE_TOP: 96,        // 自然地形+装饰的最高可达高度
CONTENT_NATURAL_TOP: 116,    // 含乐园结构
```

即 **116 以上基本恒为空气，却仍然分配并遍历**。

**目标**

- 单区块常驻内存下降 50% 以上
- `relight` 只处理非空 section
- 视距 `STREAM_RENDER_RADIUS` 能提到 12 而内存不失控（`setRenderRadius` 当前硬 clamp 在 12）

**具体做法**

1. 引入 16 高 section（每区块 16 段），空段用 `null` 占位不分配。
2. 单一方块类型的均质段（纯石头/纯空气）用 palette + 单值压缩。
3. `relight` 与 `recomputeBlockLightAround` 按段跳过。
4. 256³ 核心也切成 section 并支持远离时卸载 —— 但**必须保持存档逐位兼容**，这是最大约束（`FiniteWorld` 的存在就是为了兼容旧档）。

**验收标准**

- `test/smoke.js` 与 `terrain_parity_test.js` 全绿（生成结果逐位不变）
- 旧版 v3/v4/v5/v6 存档全部可正常加载
- 新增内存回归测试：固定视距下 `performance.memory` 或估算值不高于基线的 50%

**风险：高。** 这是本文档中最容易引入静默数据损坏的一项。建议先在 `terrain_parity_test.js` 基础上扩充黄金值覆盖面，再动存储层。

### 5.3 光照计算异步化

**现状证据**

`relight` 扫 `32 × contentTop × 32` 加块光 flood fill，核心 overlay 是整份 256³ BFS，全部在主线程。放置一个方块会触发：`relight` + `recomputeBlockLightAround`（最多 3×3 区块）+ `markNeighborhood`（最多 9 个网格入队）。

`stream()` 已经给了 25% 预算做切片：

```js
// js/world/infinite.js:1136-1137
budgetMs = Math.max(1, +budgetMs || 4);
drainPendingRelight(Math.min(2, budgetMs * 0.25));
```

但单次 BFS 本身不可中断，仍可能超帧。

**目标**：单次光照更新主线程占用 ≤ 1ms。

**具体做法**

1. 天光传播移入生成 Worker（生成时顺带算完，避免回主线程二次遍历）。
2. 块光 BFS 改为可中断的增量队列，跨帧续算，中间态用旧值渲染。
3. 与 5.2 配合：按 section 跳过空段。

**前置**：5.1、5.2。

### 5.4 Chunk LOD 与远景

**现状证据**

```js

STREAM_KEEP_RADIUS: 8,
```

4. 雾距随 LOD 层数动态外推，替代当前固定的 `FOG_FAR: 240`。

**前置**：5.1、5.2。没有异步网格化，多一层 LOD 就是多一份主线程开销。

### 5.5 自适应画质改双向 + 抬高阈值

**现状证据**

```js

else adaptLowT = Math.max(0, adaptLowT - dt * 2);

    ...
  } else adaptCool = 120;   // 已到梯度底：拉长重试间隔
```

降档序列（`adaptStepDown()`，`js/main.js:1825-1846`）：远景视距 → 阴影 → 谷雾 → 水面反射 → 立体云 → 粒子密度 ×0.68 → 雨滴密度 ×0.68 → 流式预算 → 渲染分辨率 -0.15（底 0.55）。

两个问题：

1. **阈值太低。** 要 EMA 掉到 26fps 并维持 5 秒才动一档。保的是"能玩"，不是 60fps。
2. **单向。** 只降不升。玩家从雷暴天走进晴天洞穴，画质永远回不来。这一点在长会话里体感很差。

**目标**：稳定守住目标帧率（60 或用户设定的 `fpsCap`），并在余量充足时自动回升。

**具体做法**

1. 目标帧率取 `fpsCap`（0 时取 60），降档阈值改为目标的 90%（即 54fps）。
2. 新增 `adaptStepUp()`，与 `adaptStepDown()` 严格逆序，在 EMA 高于目标 115%（69fps）持续 20 秒后回升一档。
3. 加入迟滞与"回升失败记忆"：同一档位回升后 30 秒内又触发降档，则锁定该档位 10 分钟不再尝试，避免来回抖动。
4. 回升不弹 toast（降档才提示），避免打扰。

**工作量**：2–3 人日。这是第一梯队里唯一低成本、可独立完成的项，适合先做以获得快速反馈。

### 5.6 渲染插值（多人联机的前置条件）

> **MP 约束。** 单人阶段这只是高刷屏的锦上添花；联机阶段它是必需品，因此被提到第一梯队。

**现状证据**

固定 60Hz 逻辑步已经存在，且实现是正确的（累加器 + 步数上限 + 丢弃溢出步避免死亡螺旋）：

```js
// js/config.js 之外，js/main.js:59-61
var FIXED_DT = 1 / 60;
var MAX_FIXED_STEPS = 5;
var MAX_FRAME_DT = 0.1;
```

但累加器的余数只用于凑下一步，**没有插值**。相机在模拟内部被直接写入：

```js
// js/player/player.js:186-191
var cam = Voxel.Game.camera;
if (cam) {
  cam.position.set(pos.x, pos.y + C.EYE, pos.z);
  cam.rotation.x = Voxel.Controls.pitch();
  cam.rotation.y = yaw;
```

顺带注意：这行代码本身就是「模拟层直接写表现层」的典型，[8.1](#81-核心表现分层重构含打包器) 的分层必须把它拆开。

**为什么联机让它从可选变必需**

单人时的症状是 120Hz / 144Hz 显示器上物理仍是 60Hz 阶跃，属于「说不出哪里不对但不够顺」。

联机时症状是硬伤：远端玩家与生物的状态以 10–20Hz 到达（见 [9.5](#95-同步策略与带宽)），没有插值就是肉眼可见的跳动。这不是画质问题，是「联机看起来坏了」。

**具体做法**

1. 每个可见实体保存 `prev` / `curr` 两份变换，渲染时按 `alpha = simAccumulator / FIXED_DT` 插值。
2. **本地玩家相机的朝向例外**：视角必须走原始输入，插值会引入输入延迟。只对位置插值，旋转直取当前值。
3. 远端实体额外加约 100ms 的插值缓冲吸收网络抖动 —— 这一步可以留到 MP-1 再做，但数据结构要在本阶段预留。

**验收标准**

- 144Hz 显示器上移动视野无阶梯感
- 本地玩家转向的输入延迟不高于改造前（用高速摄像或帧计数验证）
- 单人存档回放的逻辑结果逐位不变（插值只影响渲染，不得回写模拟状态）

**工作量**：5–8 人日。单人阶段就能兑现收益，联机阶段直接复用。

### 6.3 HDR 管线 + 电影级色调映射

**现状证据**

> **MP 约束 —— 转 TS 的顺序应该反过来排。** 联机立项后，`net/protocol/` 是**收益最高的首个 TS 目标**，应该优先于业务模块。理由：网络协议是客户端与服务端之间唯一的契约，两侧对同一条消息的字段理解一旦不一致，产生的是难以复现的运行时错误（错误的物品被复制、位置漂移、状态不同步），而这类 bug 在无类型的 JS 里几乎无法静态发现。共享协议类型定义是 TypeScript 投入产出比最高的经典场景。
>
> 因此建议：ESLint 先行 → `net/protocol/` 直接用 TS 写（不是迁移，是新代码原生 TS）→ `core/` 逐步迁移 → `client/` 最后。

**影响**：`_test` 是为测试保留的接口，生产依赖意味着它永远不能删改。同时它绕过了任何封装，成为一个隐形的公共 API。

**做法**：在 `Voxel.Game` 上加正规的 `getGalaxy()` / `countInventory(id)` 只读查询方法，`_test` 内部转调它们。

**工作量**：1–2 人日。这是全文档中投入产出比最高的工程清理项，建议随时可做。

### 8.4 存档升级到 IndexedDB + 多槽 + 存档 v7

**现状证据**

```js
// js/systems/save.js:1-8
// 存档：localStorage（种子 + 时间 + 玩家 + 背包 + 修改过的方块）
var KEY = Voxel.Config.SAVE_KEY;           // 'starbound_voxel_save_v6'
var BACKUP_KEY = KEY + '_backup';
var SWAP_KEY = BACKUP_KEY + '_swap';
var QUARANTINE_KEY = KEY + '_quarantine';
```

工程质量本身很高：写后回读校验、配额/隐私模式分类、journal 交换恢复、损坏档隔离、v3–v5 迁移。**这是 localStorage 存档的上限写法。**

问题是天花板本身：

- 浏览器 `localStorage` 通常 5–10MB/源
- 只有"当前档 + 备份"两个位置，不是命名槽
- 其他恒星系档案 LRU 最多 24（`UNIVERSE.ARCHIVE_MAX_SYSTEMS: 24`）
- 大基地 + 多行星箱子会撞 `QuotaExceededError`

**后果**：建造成果无法成为玩家身份。一个体素沙盒如果玩家不敢大规模建造（怕撞配额），核心创造循环就被削弱了。

**做法**

1. 迁移到 IndexedDB（配额通常是磁盘的百分比，可达 GB 级），`localStorage` 保留为迁移来源与降级路径。
2. 多命名槽 + 缩略图 + 游玩时长。
3. 存档导出/导入为文件（这一步成本极低但用户价值很高，可以先做）。
4. 云同步作为可选项，依赖后端，优先级最低。

> **MP 约束 —— 必须同时完成 v7 的世界/玩家切分。** 联机立项后，这一项不能只做存储介质迁移，否则等 MP-2 做「玩家断线重连后恢复自己的背包」时要再改一次存档格式，而存档格式的每次变更都要带一套迁移代码和迁移测试。
>
> 好消息是 v6 的字段已经天然沿这条线分布（详见 [9.4](#94-存档-v6-已经存在的天然接缝)），v7 只需把扁平结构改成嵌套：
>
> ```
> { v: 7,
>   world:   { seed, time, weather, edits, meta, drops, galaxy },
>   players: { [playerId]: { player, inv, cnt, gear, held*, craftGrid, bed, dur, progress, shipFlight } } }
> ```
>
> 单人模式就是「只有一个 player 条目」的特例，不需要两套代码路径。

**工作量**：15–25 人日（含 v7 迁移与迁移测试；联机决策前的估算是 12–20）。

## 9. 多人联机（已立项）

> **决策：方案 A —— 专门立项。** 本节是据此制定的工程方案，不再是选项分析。

### 9.1 现状

零网络代码。全库无 WebSocket / WebRTC / 同步协议。README 明确列为已知限制：

> 单进程世界（无多人联机）

唯一的 `storage` 事件监听是同浏览器标签页之间的设置同步，不是多人。

### 9.2 这个决策立刻改变了什么

联机的代码要到第五梯队才写，但决策**从今天起就生效**，因为它改变了前面几项的做法。三条硬约束：

| 约束 | 影响的章节 | 如果不遵守会怎样 |
|---|---|---|
| 权威模拟必须零渲染依赖，能在 Node 里跑 | [8.1](#81-核心表现分层重构含打包器) | 拆分轴画错，MP-1 开工时整个重构重做 |
| 渲染插值从可选变必需 | [5.6](#56-渲染插值多人联机的前置条件) | 远端实体以 10–20Hz 到达，肉眼跳动 |
| 存档 v7 按「世界共享 / 玩家私有」切分 | [8.4](#84-存档升级到-indexeddb--多槽--存档-v7) | 存档格式要改两次，每次都要带迁移代码与测试 |

还有一条软约束：TypeScript 的迁移顺序应该以 `net/protocol/` 打头，而不是从业务模块开始（见 [8.2](#82-typescript-或至少-eslint--jsdoc)）。

### 9.3 这个代码库的四个先天优势

立项前我判断这是「架构最抗拒的改动」。深入审计后，结论要修正得乐观一些 —— 这个代码库对联机的适配度**远高于预期**，有四项现成资产：

**一、确定性生成 = 不需要同步地形。**
世界由种子四级确定性派生（宇宙 → 银河 → 恒星系 → 行星），且已有 `test/terrain_parity_test.js` + `terrain_golden.json` 守护逐位一致性。客户端本地生成地形，网络只传编辑增量。这直接砍掉了体素联机中最大的带宽开销。

**二、存档格式已经就是网络状态模型。**
v6 payload 存的是 `seed` + `edits` + `meta`，且 `pruneForSave` 明确丢弃可再生的世界快照：

```js
// js/systems/save.js:268-270
// 无限宇宙瘦身：存档前丢弃可再生的世界快照并 LRU 裁剪其他恒星系档案。
if (obj.galaxy && Voxel.Galaxy && Voxel.Galaxy.pruneForSave) {
  try { obj.galaxy = Voxel.Galaxy.pruneForSave(obj.galaxy); } catch (pruneError) { }
```

「只持久化不可再生的增量」正是新玩家加入时需要传输的全部世界状态。加入流程可以直接复用存档序列化。

**三、固定 60Hz 步长已经存在且实现正确。**
`FIXED_DT = 1/60`、`MAX_FIXED_STEPS = 5`、溢出步丢弃防死亡螺旋 —— 这是现成的 tick 基础。逻辑步与渲染帧已经分离，只差插值（[5.6](#56-渲染插值多人联机的前置条件)）。

**四、模拟层对 three.js 的依赖极浅。**
`js/entities/mobs.js` 1166 行只有 18 处 `THREE.` 引用，其中 4 处只是把 `Vector3` 当数学容器用；`js/player/` 整个目录只有 6 处。真正难剥离的渲染代码集中在 `js/world/mesh.js` 与各视觉系统 —— 而那些本来就属于 client 层，不需要剥离。

### 9.4 存档 v6 已经存在的天然接缝

v6 的 17 个顶层字段可以干净地按「世界共享 / 玩家私有」二分，没有需要拆开的复合字段：

| 世界共享 | 玩家私有 |
|---|---|
| `seed` — 世界种子 | `player` — 位置、朝向、生命、饥饿 |
| `time` — 昼夜相位 | `inv` / `cnt` / `dur` — 背包、堆叠数、耐久 |
| `weather` — 天气状态 | `gear` — 装备槽 |
| `edits` — 方块修改增量 | `held` / `heldCnt` / `heldDur` — 光标持有物 |
| `meta` — 容器内容 | `craftGrid` / `invCraftGrid` — 临时合成格 |
| `drops` — 地面掉落物 | `bed` — 重生点 |
| `galaxy` — 星系档案（含已访问标记，部分私有） | `progress` — 教程 / 成就 / 图鉴 |
| | `shipFlight` — 飞船状态 |

唯一需要设计判断的是 `galaxy`：星系的**存在与地形**是共享的，但**发现状态与访问记录**应该是私有的（否则一个玩家的探索会替所有人解锁图鉴）。建议拆成 `world.galaxy`（客观）+ `players[id].discovered`（主观）。

### 9.5 同步策略与带宽

| 内容 | 通道 | 频率 | 权威方 | 备注 |
|---|---|---|---|---|
| 方块编辑 | 可靠有序 | 事件驱动 | 主机 | 复用 `edits` 结构 |
| 玩家位置/朝向 | 不可靠 | 20Hz | 主机校正 | 客户端预测 + 和解 |
| 生物状态 | 不可靠 | 10–20Hz | 主机 | 客户端插值 |
| 背包 / 合成 / 容器 | 可靠 | 事件驱动 | 主机 | 防物品复制的关键 |
| 时间 / 天气 | 可靠 | 低频 | 主机 | |
| 区块数据 | **不传** | — | — | 双方由种子各自生成 |

**带宽是可控的**，因为生物数量本来就有硬上限：

```js
// js/config.js:79-83
MOB: {
  SHEEP_TARGET: 8, ZOMBIE_TARGET: 6,
  PIG_TARGET: 5, CHICKEN_TARGET: 5, RABBIT_TARGET: 4, CAT_TARGET: 8,
  ARCHER_TARGET: 2, BOOMER_TARGET: 2,
```

同世界实体总数在几十量级。4–8 人会话下，稳态带宽估计在几十 KB/s，远低于视频通话。峰值出现在大规模挖建时的编辑洪流，需要做批合并与限流。

### 9.6 需要重新设计的既有系统

按难度排序，前两项是真正的硬骨头：

**1. 跨世界会话（本项目独有的最大难点）。**
玩家可能同时身处不同行星、甚至不同恒星系。Minecraft 的「维度」模型不能直接套用，因为这里的世界是**无限多且按需生成**的。需要设计「一个会话内多个活跃世界实例」的模型，并决定：主机离开某世界后，留在那里的玩家怎么办？空世界是否继续模拟（作物生长、熔炉烧制）？建议 MP-1/MP-2 阶段强制所有玩家同世界，把这个问题推迟到 MP-3。

**2. 玩家状态去单例化。**
`inv` / `gear` / `sel` / `bed` 等目前是 `js/main.js` 的闭包变量（见 8.1 的分区表，1–117 行）。要变成 per-player 实体集合。这是 8.1 重构中工作量最大的单点。

**3. 兴趣管理。**
`js/world/infinite.js` 的 `focus` 是单点，`refreshStreaming()` 围绕它计算工作集。多人需要 per-player 的流式集合与并集卸载判定。

**4. 暂停语义。**
当前 ESC 暂停时世界照常运转、仅冻结玩家操作（`fixedUpdate` 里的 `frozen` 标记）—— 这个设计对联机友好，改动小。但「睡觉跳过夜晚」需要改成多人投票机制。

**5. 难度与死亡。**
「噩梦」难度是死亡删档。多人会话里一人死亡如何处理？建议联机会话禁用噩梦难度，或改为仅删除该玩家的进度。

**6. 进度归属。**
教程、成就、图鉴、村民委托、终局清单卡 —— 每一项都要判定共享还是私有。建议：成就与图鉴私有，村民委托与嘉年华设施状态共享。

**7. 共享交互对象。**
嘉年华乘坐设施、售票亭、熔炉、箱子需要并发访问控制（两个玩家同时开同一个箱子）。

### 9.7 分期

**MP-0：无渲染核心验证**（10–15 人日，前置 8.1）
在 Node 里加载 `core/`，跑通「建世界 → 放方块 → 600 个固定步 → 存档读档」，全程不加载 three.js。产出一个进 CI 的测试。这是 8.1 边界正确性的**证明**，不是联机功能本身。

**MP-1：双人同世界走动与挖建**（30–50 人日）
WebRTC DataChannel 直连 + 最小信令。同一行星、同一世界，同步玩家位置与方块编辑。生物暂不同步（先只在主机侧存在且不广播）。目标是验证协议骨架与预测和解，不是完整玩法。

**MP-2：完整共享玩法**（40–70 人日）
生物同步、背包与容器的权威化、掉落物、战斗、天气时间、共享交互对象、断线重连与状态恢复。会话规模 4–8 人。这一期结束时联机是「可玩且好玩」的。

**MP-3：跨世界会话 + 专用服务器**（25–45 人日）
多世界实例、跨星系分散的玩家、Node 专用服务器（复用同一份 `core/`）、主机迁移。

### 9.8 传输与基础设施

**MVP 用 WebRTC DataChannel P2P + 主机权威**，不用 WebSocket 服务器。理由：这个项目部署在 GitHub Pages（纯静态），P2P 能把后端依赖压到最小。

但要正视一个代价：**这会引入项目的第一个后端依赖。** WebRTC 需要信令来交换 offer/answer。三个层次的选择：

1. **手动交换**（MP-1 验证期）：把 offer/answer 编码成一串文本让玩家自己复制粘贴。零基础设施，够用来验证协议，体验很差但不阻塞开发。
2. **极小信令服务**（MP-2 起）：Cloudflare Workers / Deno Deploy 免费层足够，代码量约百行。
3. **专用服务器**（MP-3）：可选，给想要 7×24 世界的玩家。

**必须守住的底线**：单人模式在 `file://` 下完全可用、零网络请求。联机是增量能力，不是替换。

### 9.9 成本修正

| 项 | 原估算 | 修正后 | 变化原因 |
|---|---|---|---|
| 8.1 核心/表现分层 | 25–40 | **40–60** | 拆分轴改变 + 彻底去渲染依赖 + `net/` 命令入口 |
| 5.6 渲染插值 | 未列 | **5–8** | 从可选优化提为必需项 |
| 8.4 存档 | 12–20 | **15–25** | 增加 v7 世界/玩家切分与迁移 |
| MP-0 ~ MP-3 | 120–250（笼统） | **105–180** | 确定性生成与存档格式复用带来的下调 |

**联机专项总计约 105–180 人日**，加上被它抬高的前置成本约 25–35 人日。

估算下调的依据是 9.3 的四项先天优势 —— 特别是「不需要同步地形」和「存档格式即状态模型」，这两条在多数体素项目里都要从零建设。

### 9.10 风险登记

| 风险 | 等级 | 缓解 |
|---|---|---|
| 跨世界会话设计失败 | 高 | MP-1/MP-2 强制同世界，推迟到 MP-3 |
| 8.1 边界画得不够干净，MP-1 时才发现 | 高 | MP-0 作为强制门禁，进 CI |
| 主机权威 → 主机玩家有天然延迟优势 | 中 | 好友局可接受；MP-3 的专用服务器解决 |
| 后端依赖破坏「零后端、可离线」属性 | 中 | 单人路径完全不走网络，信令仅在开房时使用 |
| 预测和解在体素编辑上出现分歧（幽灵方块） | 中 | 方块编辑走可靠有序通道，不做预测，接受一个 RTT 的延迟 |
| 确定性在不同浏览器上被浮点差异破坏 | 中 | `terrain_parity_test.js` 扩展到多浏览器 CI |
| 范围蔓延到「100 人服务器」 | 中 | 明确写死 4–8 人合作局的目标 |

### 9.11 明确的非目标

写下来是为了防止范围蔓延：

- **不做大规模服务器**（数十上百人同世界）。那是另一个工程问题，需要区域分片与专业运维。
- **不做反作弊。** 目标是好友合作局，主机权威已足够防止意外，不防恶意。
- **不做跨会话持久化的公共服务器**（MP-3 之前）。
- **不做玩家账号体系。** 用会话内昵称即可。
- **不做语音。** 让玩家用 Discord。

## 10. 明确不建议做的事

### 10.1 不要做高清 PBR 贴图

16px 程序化图集是**风格资产，不是技术妥协**：

```js
// js/blocks.js:836-840
var atlasCanvas = null, atlasTexture = null;
// v8 图集升格：512×512（32×32=1024 个 16px tile），彩色变体批量绘制需要余量
var ATLAS_SIZE = 512;

```

上传设置也已经调优过：

```js
// js/blocks.js:2397-2403
atlasTexture = new THREE.CanvasTexture(atlasCanvas);
atlasTexture.magFilter = THREE.NearestFilter;
// 近处保持 Nearest 的像素锐度；mipmap 链在斜视/远距时平滑掉摩尔纹闪烁。
atlasTexture.minFilter = THREE.NearestMipmapLinearFilter;
atlasTexture.generateMipmaps = true;
atlasTexture.anisotropy = 8;
```

Minecraft RTX 保持了 16px 像素风，照样是 3A 级观感 —— **差距在光照层，不在贴图分辨率**。换成高清贴图会毁掉美术统一性，同时把首屏体积从程序化的近乎零推到几十 MB。

### 10.2 不要再加第 25 个生物群系

已有 24 个群系（`js/world/biomes.js`，404 行，`B.OCEAN` 到 `B.NORDIC_FJORD`）。数量已经过剩，缺的是**每个群系里的差异化遭遇**（见 7.1）。再加群系只会稀释已有内容的密度。

### 10.3 不要在第一梯队完成前上 SSAO / SSR / 体积光

最坏帧 120ms 的基础上叠全屏 pass 是负收益。而且一旦上了，第一梯队的优化成果会被这些效果吃掉，无法验证是否真的改善了。

### 10.4 不要在阶段 2 完成前写任何联机代码

联机已立项，但**立项不等于现在动手**。在核心/表现分层（8.1）与 MP-0 门禁通过之前写网络代码，会把同步逻辑焊死在还没拆开的上帝对象上，产生比现在更难拆的耦合。

判断标准很明确：**MP-0 没进 CI 绿灯，就不写 `net/` 下的任何实现。**

反过来说，从今天起每一个改动都要遵守 [9.2](#92-这个决策立刻改变了什么) 的三条硬约束 —— 那不是"以后再说"，那是现在就生效的。

### 10.5 不要让联机范围蔓延成"大规模服务器"

目标是 4–8 人好友合作局。数十上百人同世界是完全不同的工程问题（区域分片、专业运维、反作弊、账号体系），会把 105–180 人日的预算变成不可控。非目标清单见 [9.11](#911-明确的非目标)，建议贴在项目看板上。

### 10.6 不要盲目重写

这个代码库有大量**已经解决的难题**，重写会全部丢失：确定性世界生成与 v3→v6 存档迁移、Worker 失效回退、区块流式的活锁防护、触控手势与座舱交互、51 个测试构成的回归网、无障碍与移动端适配、音频懒加载与首屏预算契约。

这些东西的价值在代码里看不出来，在重写时才会痛。**所有改动都应该是原地演进，不是推倒重来。**
